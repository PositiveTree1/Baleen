# Scoped wallet setup

Current operator status: Deposit Wallet and approved builder session-management access are **not set up yet**. No wallet has been funded, authorized, or traded by this review.

1. Identify or create the intended Polymarket Deposit Wallet through the official account flow. Retain the owner in the user's wallet; never put its private key into Baleen. Confirm the wallet type and public owner/account addresses. See [Wallets and Authentication](https://docs.polymarket.com/trading/wallets-auth).
2. Create the integration's Builder API credentials and request approval for session-key management through Polymarket's builder support. The current beta requires that approval. The operator sends this request themselves; no message was sent on their behalf. See [Session Keys](https://docs.polymarket.com/trading/session-keys).
3. Configure `POLYMARKET_BUILDER_API_KEY`, `POLYMARKET_BUILDER_SECRET`, and `POLYMARKET_BUILDER_PASSPHRASE` in the backend's secret manager. Configure a trusted Polygon RPC as `POLYGON_SETTLEMENT_RPC_URL`. These are server settings, never `NEXT_PUBLIC_*` variables or work-report contents.
4. Save the wallet's owner-authenticated CLOB API credentials in the authenticated Baleen credential form with signature type 3, the Deposit Wallet address and its owner signer address. These API credentials are not the owner's private key. Preparing a session checks the wallet identity through an authenticated venue read, then generates a separate encrypted session key.
5. Review and approve the fixed-purpose session challenge in the owner wallet. The browser helper checks Polygon, owner identity, wallet/session addresses, the exact authorize/revoke call and expiry before requesting the signature. The backend separately recovers the owner and verifies the persisted challenge. Authorization requests grant CLOB scope only and use the venue-required lifetime. Relayer acceptance remains pending until grant verification observes it.
6. To stop, disable local signing immediately, then use an owner-approved revocation request. Local disable and a relayer acknowledgement do not prove on-chain revocation. Keep pending/unknown operation records and verify the outcome; do not recreate a session to bypass an uncertain request.

The new API and signing helper are implemented; Settings controls are assigned in `GEMINI_FINISHING_WORK.md`. The `initialize-account` endpoint saves actual confirmed funding with execution disabled; it rejects existing orders and positions whose basis has not been imported. This setup does not activate copying or close the remaining engineering and acceptance work in [LIVE_READINESS_REVIEW.md](../LIVE_READINESS_REVIEW.md). Keep `LIVE_EXECUTION_ENABLED=false`. Do not seed a live balance with paper cash.
